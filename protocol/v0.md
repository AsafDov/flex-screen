# Deck ↔ companion protocol, v0

Newline-delimited JSON over the deck's USB CDC serial port (USB ID `1209:0001`, product
"flex-screen deck"). One JSON object per line, UTF-8, `\n` terminated, at most 8 KB. Every
object has a `t` (type) field. Unknown types and fields are ignored, so either side can be
updated first.

The companion owns the state and pushes a full snapshot of a topic whenever it changes;
the deck never asks for deltas. The deck sends actions; it never changes PC state itself.

## Connection

- Baud rate is meaningless over USB CDC, **except 1200**: changing the line coding to
  1200 baud reboots the deck into its ROM bootloader (that's how uploads work). The
  companion opens at 115200. DTR/RTS patterns never reboot the deck.
- The deck only writes while the host has both **DTR and RTS** up.
- Handshake: after opening, the companion drops RTS and DTR, raises DTR then RTS, waits
  100 ms and sends `sync`. The deck answers every `sync` with `hello` (and never says
  hello otherwise). No valid reply within 5 s → the companion repeats the handshake.
- On every `hello` the companion sends `time`, the album art, and every state topic.
- The companion sends `ping` every 2 s. The deck treats the companion as gone after 5 s
  of silence and falls back to plain HID media keys.

| `call` | `app` (`teams`, `zoom`, `discord`, `webex`, `browser`, or "" for no call), `name`, `secs` (into the call), `mic_muted`, `camera` (1/0/-1 unknown), `hand` (1/0/-1), `deafened`, `can` (of `mic`, `camera`, `hand`, `deafen`, `leave`, `react`), `note` (a setup hint), `volume` (the app's, or -1). | `pc` | `locked`, `idle` (seconds since the PC's last keyboard or mouse input), every 2 s: with the deck's own touches, they decide its idle screen |
| `kbd` | A VIA/Vial keyboard (the Corne): `present`, `name`, `layer` (the highest active one) and `label` (settings.json's `layerNames`, by default "BASE", "NAV", "SYMBOL"; else "LAYER n"). `held_ms`: how long the key holding that layer on has been down (-1 when the layer is toggled on, or the base one), and `key`, that key's index in `keymap.keys` (-1 for none) |
| `keymap` | The layer cheat sheet, from a Vial keyboard's own definition and keymap: `keys`, one `[x, y, w, h]` per key in hundredths of a key from the keyboard's top-left (x, y the centre; rotated thumbs at their turned centre; a split keyboard's halves moved to half a key apart), and `layers`, each `{n, name, keys, dim}`: a label per key ("top\nmain\nbottom" or just "main": the top line a modifier combined with the key, the bottom what holding it does) and `dim`, a '1' for each key the layer leaves transparent (labelled with the base layer's key). | `git` | The current repo: `repo`, `branch`, `ahead`, `behind`, `m`, `a`, `del`, `u` (modified, added, deleted, untracked file counts), `last` (last commit's subject), `last_secs`, `busy` (the operation running, or ""), `error` ("Not a git repository", …) |

All `secs` are as of sending; the deck counts on from there.

### Images

Icons (windows', the context bar's app, and the Recent and shortcut tiles') are `img` with `kind` `"icon"`: 32×32,
`fmt` `"rgb565a8"` (the RGB565 plane, then an 8-bit alpha plane: 3072 bytes, one part).
They're sent before the `windows`, `context`, `actions` or `shortcuts` state that first refers to them.

Album art is a 180×180 square, `fmt` `"rgb565"` (little-endian 16-bit, LVGL's native
format). It's split into parts of 3072 raw bytes (4096 base64 characters) so each line
stays small; `off` is the part's byte offset, so parts can arrive in any order. The
companion pauses 25 ms between parts so the deck's 32 KB receive buffer never fills, even
while a full redraw holds up its loop. The
`img` parts always arrive before the `media` state whose `art` refers to them; `id` is a
content hash, so the deck can skip a repeat.

A part that doesn't decode to its 3072 bytes (or the remainder, for the last) is a
`log` "img <id>: bad part <n>": bytes lost in transit can leave a line that still parses.

### Losses

All writes to the deck are held to about 64 KB/s. When the deck logs `receive buffer
overflowed`, `bad line` or a bad image part, the companion sends every state topic again
1.5 s later (at most every 5 s), and the album art; window icons the deck lacks it asks for
with `icon.need`. The deck skips a `state` line identical to its topic's last one (until the
port reopens or it says `hello`), so a repeat costs nothing.

## Firmware updates

`firmware/scripts/ota_upload.py` (run by `pio run -t upload`) updates the deck over this
link; the running firmware writes the image into its spare app slot. The uploader opens
the port without toggling DTR/RTS and sends `sync` until it gets `hello`, then:

| Direction | `t` | Fields | Meaning |
|---|---|---|---|
| → | `ota` | `size` | Start an update of `size` bytes. |
| ← | `ota_ready` | `size` | Slot erased and ready. |
| → | `ota_data` | `off`, `b64` | The next 4096 bytes (one flash sector) at byte offset `off`. Parts must arrive in order. |
| ← | `ota_ack` | `off` | Bytes received so far. The uploader waits for this before the next part. |
| → | `ota_end` | | Verify the image and make it the boot slot. |
| ← | `ota_done` | | Done; the deck restarts ~300 ms later. |
| ← | `ota_error` | `msg` | Anything failed; the update is abandoned and the old firmware keeps running. |

Firmware 0.2.2 checked `off` against Arduino's `Update.progress()`, which trails one
sector behind; the uploader sends that build the offset it expects.

## The companion's local endpoint

The companion listens on `http://localhost:48151` (this PC only, no admin rights needed):

- `POST /claude/usage`: `{"five_hour": 42, "seven_day": 17}` (percent used; `seven_day`
  optional), from a server's hooks (`~/.claude/flex-screen-usage.sh`, which runs Claude
  Code's own `/usage` there). The Usage key shows it, and the PC's own reading waits while
  these keep coming (15 minutes).
- `POST /claude`: Claude Code hooks post each event's JSON (what the hook gets on stdin)
  here (a server's hooks over an SSH tunnel add an `X-Claude-Model` header: the model of
  the session's last reply, from its transcript there), for `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`,
  `Notification`, `Stop` and `SessionEnd`. The hooks live in `~/.claude/settings.json`,
  added by `flex-screen-companion.exe --install-hooks` (`--uninstall-hooks` removes them);
  each runs `curl.exe` directly and asynchronously, so Claude never waits on it. Both the
  CLI and the Claude extension in VS Code read that file.
- `POST /test`: a message as if the deck had sent it, for testing without touching the
  deck. Only `{"t":"act"}` with `win.focus`, `win.close`, `icon.need`, `claude.approve`, `claude.deny`, `zone.snap` (which
  also takes `hwnd`, to snap a given window instead of the foreground one) or
  `zone.layout`, and `{"t":"bench"}`, which goes on to the deck. Needs the header
  `X-Flex-Screen-Test: 1`.
- `POST /deck`: `{"t":"page","i":n}` switches the deck's page; `{"t":"shot"}` answers
  with a PNG of the deck's screen (800×480, ~2.5 s), for checking layouts on the real
  board. The deck sends its frame buffer as `{"t":"shot","w","h","i","n","d"}` lines,
  `d` being 3 KB of RGB565 (little-endian, row by row) in base64. Needs the test header.
- `/claude`, `/test` and `/deck` refuse requests with an `Origin` header: browsers send one
  with every cross-site request (and can't add the custom header without a preflight),
  so a web page can't reach them.
- `GET /vscode` (WebSocket): one connection per VS Code window, from the extension in
  `vscode-ext/`. JSON text frames:

| Direction | `t` | Fields | Meaning |
|---|---|---|---|
| ext → | `hello` | `version`, `window`, `remote`, `name`, `folders`, `focused`, `claude` | On connecting, and when the workspace folders change. `claude` (0.4.0 on): as for the `claude` message. `version` is the extension's (0.2.1 on; missing means 0.1.0): a VS Code window keeps the extension it started with until it's reloaded. `remote` is VS Code's remote name (`ssh-remote`, `wsl`, `dev-container`…) or "" for a local window; a remote window's `folders` are paths on that machine, so the companion doesn't run git on them. The extension runs on the PC even in a remote window (`extensionKind` `ui` first), since the companion is only on the PC's localhost. |
| ext → | `focus` | `focused` | The window gained or lost focus. |
| ext → | `claude` | `front` | Claude Code's chat tab (its `claudeVSCodePanel` webview) became, or stopped being, the active tab of the active editor group (0.4.0 on). The context bar is Claude's meanwhile. |
| ext → | `term.start` | `id`, `cmd`, `cwd`, `terminal` | A command started in an integrated terminal (shell integration). |
| ext → | `term.data` | `id`, `lines` | Its last 8 lines of output so far, at most every 300 ms. |
| ext → | `term.end` | `id`, `exit`, `ms` | It finished; `exit` is null if the shell didn't report one. |
| ext → | `term.history` | `items`: up to 8 of `{cmd, exit, ms, at, running, lines}`, newest first | The workspace's last commands (kept in VS Code's workspace state, so they outlast restarts), on connecting and whenever one starts or ends; `at` is when it ended (started, while running) in Unix ms, and only the newest has `lines`. The companion shows the list of the window with the newest command, and after its own restart that command's output too. |
| ext → | `task.start` / `task.end` | `name`, `group`, `source`, and `exit` on end | A VS Code task ran. |
| → ext | `replay` | `cmd` | Run it again in the terminal it last ran in, if that's open and idle, else in the extension's own "flex-screen" terminal at the workspace root (a second one opens while it's busy). |
| → ext | `interrupt` | | Send Ctrl+C to that terminal. |
| → ext | `terminal` | | Show that terminal. |
| → ext | `scm` | | Open the Source Control view. |
